# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An Electron desktop app that wraps `yt-dlp` (and `ffmpeg`, needed for stream merging as well as audio extraction) with a simple UI to download YouTube videos/playlists or extract audio as MP3. The app ships no binaries — yt-dlp/ffmpeg are downloaded on demand via a "Dependencies" panel in the UI. A second, separate entry point (`src/mcp/server.js`) exposes the same download functionality as an MCP server, so an MCP client (e.g. Claude Desktop/Code) can trigger a download directly instead of going through the GUI — see "MCP server" below.

## Commands

```bash
yarn install          # install deps (postinstall runs electron-builder install-app-deps)
yarn dev              # = yarn electron: launch the app
yarn mcp              # launch the MCP server (stdio transport) — for use from an MCP client, not interactively
yarn eslint           # lint + autofix ./src/frontend (backend is not linted)
yarn build-mac        # package for macOS (dmg)
yarn build-linux      # package for Linux (deb)
yarn build-win        # package for Windows (nsis)
yarn build-all        # build for all platforms (electron-builder -mwl)
```

There is no test suite. electron-builder cannot cross-compile native deps — build a platform's target only on that platform.

## Architecture

Plain Electron main/renderer split, no bundler/framework — `src/frontend` is loaded directly as static HTML/CSS/JS.

- `src/backend/index.js` — main process entry point. Creates the `BrowserWindow` (context isolation on, node integration off), ensures the `~/youtube-downloader` output directory exists, and wires `ipcMain` handlers: `download` (a thin wrapper around `download.run`, see below), `abort`, `explore` (opens the output folder in the OS file manager), plus the `dependencies:*` handlers described below.
- `src/backend/preload.js` — the only bridge between renderer and main. Exposes `window.api.on(channel, fn)` / `window.api.send(channel, data)` / `window.api.invoke(channel, data)` via `contextBridge`. Any new IPC channel must be added here to be reachable from the frontend.
- `src/backend/commandante.js` — thin wrapper around `child_process.spawn` for running the `yt-dlp`/`ffmpeg` command as an argv array (`spawn(binary, args, options)`, no shell), streaming stdout/stderr back via `onLogs`/`onExit` callbacks, and killing the process tree (`tree-kill`) on abort. Does **not** pass an `env` override — `spawn()` must inherit the full parent environment (`HOME`, `PATH`, ...) by default. A previous version set `env: process.env.PATH` (a string, not an object); `child_process` silently coerces a non-object `env` by enumerating it, so the child got numeric-indexed junk instead of real variables — `HOME` came out empty (breaking anything reliant on it: shell rc files, nvm-managed `node` on `PATH`, etc.).
- `src/backend/download.js` — builds the yt-dlp argv from a form config (`buildArgs`, now `async`) and runs it via `commandante` end-to-end including exit-time comments/captions cleanup (`run`). Extracted so the Electron IPC handler and the MCP `download_media` tool share one implementation instead of duplicating the flag logic. When `includeCaptions` is set, `buildArgs` first awaits `resolveCaptionLang` — a metadata-only `yt-dlp -j --skip-download` pre-flight call (doesn't touch the rate-limited caption-content endpoint) that checks which of the two known-duplicate English auto-caption tags (`en`/`en-orig`, see captions.js below) the video actually has, and sets `--sub-langs` to request only that one instead of both. If neither exists, the subtitle flags are skipped entirely rather than issuing a request guaranteed to come back empty. Falls back to the old broad `en$,en-orig$,-live_chat` pattern if the lookup itself fails or returns unparseable output.
- `src/backend/utils.js` — platform detection (`isLinux`/`isMac`/`isWin`), used to pick download URLs/binary filenames; `createFolderIfNotExists`; and `getUserDataDir(appName)`, which reimplements Electron's own `app.getPath('userData')` resolution without depending on the `electron` module, so `dependencies.js` resolves to the identical directory whether run from the Electron main process or the plain-Node MCP server (one shared yt-dlp/ffmpeg install either way).
- `src/backend/dependencies.js` — resolves/installs/updates the managed yt-dlp and ffmpeg binaries (see below). No `electron` import — uses `utils.getUserDataDir` instead of `app.getPath('userData')`, which is what makes it (and everything built on it) usable from the MCP server.
- `src/backend/comments.js` — `writeReducedComments(infoJsonPath, outputPath, minLikes, minTextLength)` strips a yt-dlp `.info.json` down to just `{author, text, like_count}` per comment, drops any comment below `minLikes` and/or shorter than `minTextLength`, and sorts by `like_count` descending (the raw file also carries the full video metadata plus per-comment noise like `author_thumbnail` URLs — routinely ~3-4x larger than the fields anyone actually wants).
- `src/backend/captions.js` — `writeCleanCaptionsFromDir(subsDir, outputDir)` turns a converted `.srt` into a single flowing `.md` transcript: YouTube's auto-captions "roll up" (each cue repeats the previous cue's text plus one new line), so it drops any line identical to the last one kept. If more than one English track was fetched for the same video id (e.g. a translated `en` alongside the original-language `en-orig`), it picks `en` over the rest rather than writing duplicate output files — this is now mostly a defensive fallback, since `download.js`'s `resolveCaptionLang` pre-flight check (see above) usually requests only one of the two to begin with.
- `src/frontend/js/storage.js` — `window.storage.loadLastConfig()` / `saveLastConfig(config)`, a thin `localStorage` wrapper (key `youtube-downloader:lastConfig`). Renderer-only, no IPC needed — Electron's renderer has plain browser `localStorage` regardless of `contextIsolation`.
- `src/frontend/js/client.js` — renderer logic. Renders a JSON Schema form via [Jedison](https://github.com/germanbisurgi/jedison) (`Jedison.Create({container, theme: new Jedison.ThemeBootstrap5(), iconLib: 'bootstrap-icons', schema, data})`) — `url`, `media` (enum `'none'|'video'|'audio'`, default `'none'`), `includeCaptions`, `includeComments`, `minLikes`, `minTextLength`, `cookiesFromBrowser` — passing `storage.loadLastConfig()` as `data` so the form reopens with whatever was last entered, and saving on every `jedisonForm.on('change', ...)`. Sends the form value over `download`, streams `logs`/`exit` events into a `<textarea>`, and drives the Dependencies panel (status badges + Install/Update buttons) via `dependencies:*` IPC. Was `@json-editor/json-editor` + Bootstrap 4 until switched to match `mcp-whisper`'s stack exactly (see below) — same library, same Bootstrap major version, so the two apps' components render identically, not just similarly colored.

**Dark theme via design tokens, Bootstrap 5 + Jedison to match mcp-whisper exactly.** `src/frontend/css/variables.css` defines the same brand design tokens as n3-stack's `admin-app/src/assets/tokens.css` (colors, radii, spacing, fonts). `theme.css` applies them by reassigning Bootstrap 5's own runtime CSS variables (`--bs-*`, `--bs-btn-*` inside `.btn-primary`/`.btn-outline-primary`) under `html[data-bs-theme="dark"]` — and is **kept identical to mcp-whisper's `theme.css`** (diffed to confirm on every change) specifically so both apps use the same Bootstrap major version with the same variable overrides, not just similar hand-tuned colors on two different Bootstrap versions (Bootstrap 4, which this app used until this switch, has no such runtime variables — see mcp-whisper's `CLAUDE.md` for why that made "identical" impossible while still on it). The Download button uses `.btn-primary` (not `.btn-success`) specifically so its color traces back to a design token via an overridden Bootstrap variable — `.btn-success` is never remapped in either app, so it would've rendered as Bootstrap's stock green instead. There's deliberately no `reset.css` (Bootstrap's own Reboot already sets `box-sizing: border-box`) and no `components.css` (the Logs `<textarea>` uses `class="form-control font-monospace"` + a `rows` attribute instead of a dedicated CSS rule) — and no inline styles anywhere.

### Managed dependencies (`dependencies.js`)

No binaries are bundled or committed. `dependencies.js` downloads yt-dlp/ffmpeg on demand into `utils.getUserDataDir('youtube-downloader')/bin` — the same path in dev and packaged builds, and the same path whether resolved from Electron or the MCP server, so there's no dev-vs-packaged or GUI-vs-MCP branching anywhere in the codebase:
- `getBinaryPath(name)` / `isInstalled(name)` — path resolution and install-state checks; both are just `fs.existsSync`, effectively instant.
- `getInstalledFlags()` — `{installed, path}` per binary, no version lookup — this is the fast path the renderer uses to unlock Download quickly (see below).
- `getInstalledVersion(name)` / `getStatus()` — the slow path: yt-dlp's standalone binary can take **several seconds** just to report `--version` (confirmed ~11s locally), so anything that calls this should never gate the UI on it.
- `install(name, onProgress)` — downloads yt-dlp's single-file executable directly, or ffmpeg's platform-specific static-build archive (zip on mac/Windows, `.tar.xz` on Linux) and extracts it via the system `tar` (auto-detects both formats — the `extract-zip` npm package was tried first and dropped after it was found to hang indefinitely on real archives); reports `{phase, percent}` progress. Uses a single fixed scratch dir (`binDir/.tmp`), wiped at the start of every call — installing both binaries at once would let the second call delete the first one's in-flight download, so `client.js` disables **every** dependency's Install/Update button while any one of them is installing (not just the one clicked).
- `checkForUpdate(name, installedVersion)` — yt-dlp compares `installedVersion` against GitHub's `releases/latest` tag (reliable); ffmpeg does a best-effort per-platform version probe and defaults to "no update" rather than risk a false positive, since static-build hosts don't expose a clean version API. Takes `installedVersion` as a parameter instead of calling `getInstalledVersion` itself — re-deriving it here would silently double the slow yt-dlp `--version` cost on every launch.
- IPC: `dependencies:installed` (fast), `dependencies:status` / `dependencies:check-update` / `dependencies:install` (all `invoke`/`handle`), `dependencies:progress` (main → renderer `send`/`on`, streamed during an install).

`client.js`'s `refreshStatus()` calls `dependencies:installed` first and unlocks Download immediately (near-0ms) once both report `installed`, then separately calls `dependencies:status` (slow) and `dependencies:check-update` (passing the version `status` already returned) purely to update the badge text — neither of those two ever re-blocks Download.

`download.run` (called by both the `download` IPC handler and the MCP `download_media` tool) gets both binary paths from `dependencies.getBinaryPath(...)` and refuses (logs + `exit`) if either isn't installed — the UI is expected to keep the Download button disabled until both are, but this is a defensive backstop shared by both entry points. Command construction builds an argv array (`download.buildArgs`), passed to `commandante.command(binary, args, options)` which calls `spawn(binary, args, options)` directly — no shell, so args (a path with spaces under "Application Support", a URL, etc.) reach yt-dlp verbatim and can't be interpreted as shell syntax; nothing needs manual quoting. (An earlier version built a single command string executed via `spawn('bash', ['-c', command])`, which was vulnerable to shell injection through any unescaped arg — replaced once the MCP server made that arg model-originated rather than just GUI-form input.) `--js-runtimes node` is always added (lets yt-dlp solve YouTube's "n" signature challenge if a system Node.js happens to be on PATH — a harmless no-op otherwise, same degraded-but-working fallback as without the flag). `--sleep-requests 3` and `--sleep-subtitles 3` are always added too, after a captions-only download hit `HTTP Error 429: Too Many Requests` on the subtitle endpoint specifically (yt-dlp didn't retry that error class on its own) — the two flags pace different stages (extraction requests vs. the subtitle download itself), so both are needed; `--sleep-subtitles` is a no-op when `includeCaptions` isn't set. (Raised from an initial `1` to `3` — worth knowing this is a best-effort mitigation, not a confirmed fix: see the "known limitation" note below, which found the specific 429 traced here is YouTube rate-limiting auto-generated captions independent of pacing, not something any sleep value is guaranteed to prevent.) `--ignore-errors` is always added too — without it, a subtitle-only failure aborts the whole yt-dlp run before it ever attempts the video/audio, so a combined `media: 'video'` + `includeCaptions` download would lose the video over a captions failure. Tradeoff: yt-dlp's exit code becomes a weaker success signal (it now also swallows other per-item failures instead of surfacing them as nonzero), so don't rely on `commandante`'s `Process exit with code:` log line to mean "everything succeeded" — check the output text itself for `ERROR:`/`WARNING:` lines. `--cookies-from-browser <browser>` is added when `cookiesFromBrowser` isn't `'none'`, working around YouTube's "Sign in to confirm you're not a bot" bot-check by reusing a real logged-in browser session — Firefox works without extra OS permissions; Chrome/Safari may need Keychain access or macOS Full Disk Access to read their cookie store, which is an OS-level restriction outside this app's control. Other flags added conditionally: `--yes-playlist` + playlist output template when the URL contains `&list=`; `media` picks exactly one of `--extract-audio --audio-format mp3` (`'audio'`) or `--skip-download` (anything other than `'video'`/`'audio'`, i.e. the `'none'` default) — `'video'` needs no extra flag, it's yt-dlp's own default behavior; `--write-subs --write-auto-subs --sub-langs <resolved>$ --convert-subs srt` when `includeCaptions` is checked, where `<resolved>` is `resolveCaptionLang`'s result (`en` or `en-orig`, see `download.js` above) rather than a static pattern. ffmpeg is always required (yt-dlp needs it to merge separately-served video+audio streams, not just for audio extraction, and `includeCaptions` needs it for `--convert-subs`) regardless of `media`.

Both `includeComments` and `includeCaptions` follow the same pattern: route yt-dlp's raw output to a per-run scratch dir via a type-specific `--output` template (`infojson:<tmpDir>/%(id)s` / `subtitle:<tmpDir>/%(id)s.%(ext)s`) instead of the real output folder, then in `download.cleanup` (called from `commandante.onExit`, wired up inside `download.run`) run the corresponding module (`comments.writeReducedComments` / `captions.writeCleanCaptionsFromDir`) to write the cleaned-up file into `outputDir`, and delete the scratch dir either way (success or failure, via try/finally).

When `minLikes > 0`, `--extractor-args "youtube:comment_sort=top;max_comments=1000,200,1000,100"` is also added, sorting by relevance and capping the fetch — this is a real speedup for videos with huge comment sections, but YouTube has no actual "N+ likes" filter, so it's an approximation (top-sorted ≠ strictly likes-descending, and comments outside the cap are never seen). `comments.writeReducedComments` still applies the exact `minLikes` cutoff afterward, so correctness of the final file doesn't depend on the cap. `minTextLength` has no yt-dlp-side equivalent (nothing to fetch faster on) — it's applied only in `writeReducedComments`, alongside `minLikes`. A comment that clears an active `minLikes` threshold is exempt from `minTextLength` (kept regardless of length) — `minTextLength` only filters comments that didn't already qualify on likes.

**Known limitation — auto-caption 429s**: YouTube rate-limits its auto-generated-caption-serving endpoint independently of request pacing (confirmed via [yt-dlp#13831](https://github.com/yt-dlp/yt-dlp/issues/13831), open/maintainer-acknowledged as of writing) — `--sleep-subtitles` does not prevent it, and it's most likely to hit a video with no manual (human-authored) English subtitle, since only the auto-generated track goes through the rate-limited path. `--ignore-errors` (above) keeps this from also losing the video/audio, but captions themselves will still fail. The maintainer-confirmed workaround is to open the affected video in the browser named in `cookiesFromBrowser` and let its captions load there once, then retry the download shortly after — that primes server-side state the extracted cookies carry over. The actual fix (a PO-token provider, e.g. `bgutil-ytdlp-pot-provider`) would mean bundling and lifecycle-managing a separate companion process alongside this app — not implemented, treated as a separate, bigger piece of work if ever pursued.

**Automatic bot-check retry**: `download.run` is actually `runOnce` plus a retry wrapper. If a cookie-less attempt's output contains yt-dlp's `Sign in to confirm you` bot-check marker, `run` automatically retries once with `cookiesFromBrowser: 'firefox'` forced on, logging the retry so it's visible in both the GUI's Logs textarea and the MCP log. This only fires when the caller didn't already pass a `cookiesFromBrowser` (retrying with the same cookies that already failed would just fail again the same way). The default stays cookie-less on the first attempt — this only pays the cookie-extraction cost when YouTube actually asks for it, rather than on every call.

### MCP server (`src/mcp/server.js`)

A separate entry point, not part of the Electron app — run standalone with `yarn mcp` (stdio transport, via `@modelcontextprotocol/sdk`), registered in an MCP client's config as a local server (`command: node`, `args: ["<repo>/src/mcp/server.js"]`). Shares `outputDir` (`~/youtube-downloader`) and the managed yt-dlp/ffmpeg install with the Electron app (see `utils.getUserDataDir` above) — either entry point can install the binaries and both read/write the same output folder.

Two tools, intentionally minimal (no install/abort/explore tools — GUI-only for now):
- `check_dependencies` — read-only, wraps `dependencies.getInstalledFlags()`.
- `download_media` — wraps `download.run`, with a Zod input schema mirroring the frontend's JSON Schema form (`url`, `media`, `includeCaptions`, `includeComments`, `minLikes`, `minTextLength`, `cookiesFromBrowser`). Blocks until the yt-dlp process exits and returns a JSON object that always has `outputDir` and `log` (capped to the last `MAX_LOG_CHARS` characters — yt-dlp's own progress output can run to thousands of lines on a large playlist, and an MCP tool call has no separate streaming-progress channel here), plus these three keys added only when that part of the request actually produced something (an agent otherwise has to filter out empty arrays on every call just to find the one field it wanted):
  - `mediaPaths` — the final downloaded file(s), parsed out of the log via `extractMediaPaths` — checked in most-final-stage-first order, `[ExtractAudio] Destination:` before `[Merger] Merging formats into` before `[download] Destination:`, so an MCP caller doesn't have to grep the log or list `outputDir` to find what to hand to a downstream tool like mcp-whisper's `transcribe`.
  - `captions` — when `includeCaptions` was set and at least one caption file was written — `{ path, text }` per video, with `text` read back and inlined by the tool handler right after `download.run` returns, since the caption file is already a small, clean transcript and an MCP caller has no other way to discover its path — it's written by `captions.writeCleanCaptionsFromDir`, not visible in any yt-dlp log line.
  - `commentPaths` — when `includeComments` was set and at least one comments file was written, from `comments.writeReducedComments`.

  `captionPaths`/`commentPaths` flow back from `download.cleanup` through `runOnce`'s resolved `{ sawBotCheck, captionPaths, commentPaths }` and `run`'s `onExit(paths)` — added specifically because the tool handler previously had no way to return them at all.
