# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An Electron desktop app that wraps `yt-dlp` (and `ffmpeg`, needed for stream merging as well as audio extraction) with a simple UI to download YouTube videos/playlists or extract audio as MP3. The app ships no binaries — yt-dlp/ffmpeg are downloaded on demand via a "Dependencies" panel in the UI. A second, separate entry point (`src/mcp/server.js`) exposes the same download functionality as an MCP server, so an MCP client (e.g. Claude Desktop/Code) can trigger a download directly instead of going through the GUI — see "MCP server" below.

## Commands

```bash
yarn install          # install deps (postinstall runs electron-builder install-app-deps)
yarn dev              # = yarn electron: launch the app
yarn mcp              # launch the MCP server (stdio transport) — for use from an MCP client, not interactively
yarn eslint           # lint + autofix ./src/frontend (backend is not linted)
yarn build-mac        # package for macOS (dmg)
yarn build-linux      # package for Linux (deb)
yarn build-win        # package for Windows (nsis)
yarn build-all        # build for all platforms (electron-builder -mwl)
```

There is no test suite. electron-builder cannot cross-compile native deps — build a platform's target only on that platform.

## Architecture

Plain Electron main/renderer split, no bundler/framework — `src/frontend` is loaded directly as static HTML/CSS/JS.

- `src/backend/index.js` — main process entry point. Creates the `BrowserWindow` (context isolation on, node integration off), ensures the `~/youtube-downloader` output directory exists, and wires `ipcMain` handlers: `download` (a thin wrapper around `download.run`, see below), `abort`, `explore` (opens the output folder in the OS file manager), plus the `dependencies:*` handlers described below.
- `src/backend/preload.js` — the only bridge between renderer and main. Exposes `window.api.on(channel, fn)` / `window.api.send(channel, data)` / `window.api.invoke(channel, data)` via `contextBridge`. Any new IPC channel must be added here to be reachable from the frontend.
- `src/backend/commandante.js` — thin wrapper around `child_process.spawn` for running the `yt-dlp`/`ffmpeg` command as an argv array (`spawn(binary, args, options)`, no shell), streaming stdout/stderr back via `onLogs`/`onExit` callbacks, and killing the process tree (`tree-kill`) on abort. Does **not** pass an `env` override — `spawn()` must inherit the full parent environment (`HOME`, `PATH`, ...) by default. A previous version set `env: process.env.PATH` (a string, not an object); `child_process` silently coerces a non-object `env` by enumerating it, so the child got numeric-indexed junk instead of real variables — `HOME` came out empty (breaking anything reliant on it: shell rc files, nvm-managed `node` on `PATH`, etc.).
- `src/backend/download.js` — builds the yt-dlp argv from a form config (`buildArgs`) and runs it via `commandante` end-to-end including exit-time comments/captions cleanup (`run`). Extracted so the Electron IPC handler and the MCP `download_media` tool share one implementation instead of duplicating the flag logic.
- `src/backend/utils.js` — platform detection (`isLinux`/`isMac`/`isWin`), used to pick download URLs/binary filenames; `createFolderIfNotExists`; and `getUserDataDir(appName)`, which reimplements Electron's own `app.getPath('userData')` resolution without depending on the `electron` module, so `dependencies.js` resolves to the identical directory whether run from the Electron main process or the plain-Node MCP server (one shared yt-dlp/ffmpeg install either way).
- `src/backend/dependencies.js` — resolves/installs/updates the managed yt-dlp and ffmpeg binaries (see below). No `electron` import — uses `utils.getUserDataDir` instead of `app.getPath('userData')`, which is what makes it (and everything built on it) usable from the MCP server.
- `src/backend/comments.js` — `writeReducedComments(infoJsonPath, outputPath, minLikes, minTextLength)` strips a yt-dlp `.info.json` down to just `{author, text, like_count}` per comment, drops any comment below `minLikes` and/or shorter than `minTextLength`, and sorts by `like_count` descending (the raw file also carries the full video metadata plus per-comment noise like `author_thumbnail` URLs — routinely ~3-4x larger than the fields anyone actually wants).
- `src/backend/captions.js` — `writeCleanCaptionsFromDir(subsDir, outputDir)` turns a converted `.srt` into a single flowing `.md` transcript: YouTube's auto-captions "roll up" (each cue repeats the previous cue's text plus one new line), so it drops any line identical to the last one kept. If more than one English track was fetched for the same video id (e.g. a translated `en` alongside the original-language `en-orig`), it picks `en` over the rest rather than writing duplicate output files.
- `src/frontend/js/storage.js` — `window.storage.loadLastConfig()` / `saveLastConfig(config)`, a thin `localStorage` wrapper (key `youtube-downloader:lastConfig`). Renderer-only, no IPC needed — Electron's renderer has plain browser `localStorage` regardless of `contextIsolation`.
- `src/frontend/js/client.js` — renderer logic. Renders a JSON Schema form via `@json-editor/json-editor` (`url`, `media` (enum `'none'|'video'|'audio'`, default `'none'`), `includeCaptions`, `includeComments`, `minLikes`, `minTextLength`, `cookiesFromBrowser`), passing `storage.loadLastConfig()` as `startval` so the form reopens with whatever was last entered, and saving on every `editor.on('change', ...)`. Sends the form value over `download`, streams `logs`/`exit` events into a `<textarea>`, and drives the Dependencies panel (status badges + Install/Update buttons) via `dependencies:*` IPC.

### Managed dependencies (`dependencies.js`)

No binaries are bundled or committed. `dependencies.js` downloads yt-dlp/ffmpeg on demand into `utils.getUserDataDir('youtube-downloader')/bin` — the same path in dev and packaged builds, and the same path whether resolved from Electron or the MCP server, so there's no dev-vs-packaged or GUI-vs-MCP branching anywhere in the codebase:
- `getBinaryPath(name)` / `isInstalled(name)` — path resolution and install-state checks; both are just `fs.existsSync`, effectively instant.
- `getInstalledFlags()` — `{installed, path}` per binary, no version lookup — this is the fast path the renderer uses to unlock Download quickly (see below).
- `getInstalledVersion(name)` / `getStatus()` — the slow path: yt-dlp's standalone binary can take **several seconds** just to report `--version` (confirmed ~11s locally), so anything that calls this should never gate the UI on it.
- `install(name, onProgress)` — downloads yt-dlp's single-file executable directly, or ffmpeg's platform-specific static-build archive (zip on mac/Windows, `.tar.xz` on Linux) and extracts it via the system `tar` (auto-detects both formats — the `extract-zip` npm package was tried first and dropped after it was found to hang indefinitely on real archives); reports `{phase, percent}` progress. Uses a single fixed scratch dir (`binDir/.tmp`), wiped at the start of every call — installing both binaries at once would let the second call delete the first one's in-flight download, so `client.js` disables **every** dependency's Install/Update button while any one of them is installing (not just the one clicked).
- `checkForUpdate(name, installedVersion)` — yt-dlp compares `installedVersion` against GitHub's `releases/latest` tag (reliable); ffmpeg does a best-effort per-platform version probe and defaults to "no update" rather than risk a false positive, since static-build hosts don't expose a clean version API. Takes `installedVersion` as a parameter instead of calling `getInstalledVersion` itself — re-deriving it here would silently double the slow yt-dlp `--version` cost on every launch.
- IPC: `dependencies:installed` (fast), `dependencies:status` / `dependencies:check-update` / `dependencies:install` (all `invoke`/`handle`), `dependencies:progress` (main → renderer `send`/`on`, streamed during an install).

`client.js`'s `refreshStatus()` calls `dependencies:installed` first and unlocks Download immediately (near-0ms) once both report `installed`, then separately calls `dependencies:status` (slow) and `dependencies:check-update` (passing the version `status` already returned) purely to update the badge text — neither of those two ever re-blocks Download.

`download.run` (called by both the `download` IPC handler and the MCP `download_media` tool) gets both binary paths from `dependencies.getBinaryPath(...)` and refuses (logs + `exit`) if either isn't installed — the UI is expected to keep the Download button disabled until both are, but this is a defensive backstop shared by both entry points. Command construction builds an argv array (`download.buildArgs`), passed to `commandante.command(binary, args, options)` which calls `spawn(binary, args, options)` directly — no shell, so args (a path with spaces under "Application Support", a URL, etc.) reach yt-dlp verbatim and can't be interpreted as shell syntax; nothing needs manual quoting. (An earlier version built a single command string executed via `spawn('bash', ['-c', command])`, which was vulnerable to shell injection through any unescaped arg — replaced once the MCP server made that arg model-originated rather than just GUI-form input.) `--js-runtimes node` is always added (lets yt-dlp solve YouTube's "n" signature challenge if a system Node.js happens to be on PATH — a harmless no-op otherwise, same degraded-but-working fallback as without the flag). `--sleep-requests 1` and `--sleep-subtitles 1` are always added too, after a captions-only download hit `HTTP Error 429: Too Many Requests` on the subtitle endpoint specifically (yt-dlp didn't retry that error class on its own) — the two flags pace different stages (extraction requests vs. the subtitle download itself), so both are needed; `--sleep-subtitles` is a no-op when `includeCaptions` isn't set. `--ignore-errors` is always added too — without it, a subtitle-only failure aborts the whole yt-dlp run before it ever attempts the video/audio, so a combined `media: 'video'` + `includeCaptions` download would lose the video over a captions failure. Tradeoff: yt-dlp's exit code becomes a weaker success signal (it now also swallows other per-item failures instead of surfacing them as nonzero), so don't rely on `commandante`'s `Process exit with code:` log line to mean "everything succeeded" — check the output text itself for `ERROR:`/`WARNING:` lines. `--cookies-from-browser <browser>` is added when `cookiesFromBrowser` isn't `'none'`, working around YouTube's "Sign in to confirm you're not a bot" bot-check by reusing a real logged-in browser session — Firefox works without extra OS permissions; Chrome/Safari may need Keychain access or macOS Full Disk Access to read their cookie store, which is an OS-level restriction outside this app's control. Other flags added conditionally: `--yes-playlist` + playlist output template when the URL contains `&list=`; `media` picks exactly one of `--extract-audio --audio-format mp3` (`'audio'`) or `--skip-download` (anything other than `'video'`/`'audio'`, i.e. the `'none'` default) — `'video'` needs no extra flag, it's yt-dlp's own default behavior; `--write-subs --write-auto-subs --sub-langs "en.*,-live_chat" --convert-subs srt` when `includeCaptions` is checked. ffmpeg is always required (yt-dlp needs it to merge separately-served video+audio streams, not just for audio extraction, and `includeCaptions` needs it for `--convert-subs`) regardless of `media`.

Both `includeComments` and `includeCaptions` follow the same pattern: route yt-dlp's raw output to a per-run scratch dir via a type-specific `--output` template (`infojson:<tmpDir>/%(id)s` / `subtitle:<tmpDir>/%(id)s.%(ext)s`) instead of the real output folder, then in `download.cleanup` (called from `commandante.onExit`, wired up inside `download.run`) run the corresponding module (`comments.writeReducedComments` / `captions.writeCleanCaptionsFromDir`) to write the cleaned-up file into `outputDir`, and delete the scratch dir either way (success or failure, via try/finally).

When `minLikes > 0`, `--extractor-args "youtube:comment_sort=top;max_comments=1000,200,1000,100"` is also added, sorting by relevance and capping the fetch — this is a real speedup for videos with huge comment sections, but YouTube has no actual "N+ likes" filter, so it's an approximation (top-sorted ≠ strictly likes-descending, and comments outside the cap are never seen). `comments.writeReducedComments` still applies the exact `minLikes` cutoff afterward, so correctness of the final file doesn't depend on the cap. `minTextLength` has no yt-dlp-side equivalent (nothing to fetch faster on) — it's applied only in `writeReducedComments`, alongside `minLikes`. A comment that clears an active `minLikes` threshold is exempt from `minTextLength` (kept regardless of length) — `minTextLength` only filters comments that didn't already qualify on likes.

**Known limitation — auto-caption 429s**: YouTube rate-limits its auto-generated-caption-serving endpoint independently of request pacing (confirmed via [yt-dlp#13831](https://github.com/yt-dlp/yt-dlp/issues/13831), open/maintainer-acknowledged as of writing) — `--sleep-subtitles` does not prevent it, and it's most likely to hit a video with no manual (human-authored) English subtitle, since only the auto-generated track goes through the rate-limited path. `--ignore-errors` (above) keeps this from also losing the video/audio, but captions themselves will still fail. The maintainer-confirmed workaround is to open the affected video in the browser named in `cookiesFromBrowser` and let its captions load there once, then retry the download shortly after — that primes server-side state the extracted cookies carry over. The actual fix (a PO-token provider, e.g. `bgutil-ytdlp-pot-provider`) would mean bundling and lifecycle-managing a separate companion process alongside this app — not implemented, treated as a separate, bigger piece of work if ever pursued.

### MCP server (`src/mcp/server.js`)

A separate entry point, not part of the Electron app — run standalone with `yarn mcp` (stdio transport, via `@modelcontextprotocol/sdk`), registered in an MCP client's config as a local server (`command: node`, `args: ["<repo>/src/mcp/server.js"]`). Shares `outputDir` (`~/youtube-downloader`) and the managed yt-dlp/ffmpeg install with the Electron app (see `utils.getUserDataDir` above) — either entry point can install the binaries and both read/write the same output folder.

Two tools, intentionally minimal (no install/abort/explore tools — GUI-only for now):
- `check_dependencies` — read-only, wraps `dependencies.getInstalledFlags()`.
- `download_media` — wraps `download.run`, with a Zod input schema mirroring the frontend's JSON Schema form (`url`, `media`, `includeCaptions`, `includeComments`, `minLikes`, `minTextLength`, `cookiesFromBrowser`). Blocks until the yt-dlp process exits and returns the accumulated log as the tool result (capped to the last `MAX_LOG_CHARS` characters — yt-dlp's own progress output can run to thousands of lines on a large playlist, and an MCP tool call has no separate streaming-progress channel here).

### `build/`

`build/icons/` holds the app icons consumed by electron-builder; `dist/` (build output, gitignored) is where electron-builder writes packaged apps.
